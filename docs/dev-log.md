# docs/dev-log.md — Журнал разработки

## Архитектура
- **Backend:** Node.js 22 + Express 4. БД — встроенный `node:sqlite` (без нативных зависимостей).
- **Frontend:** будет подключён на следующих этапах (пока не требуется для проверки backend).
- **Auth:** scrypt (`crypto.scryptSync`), отдельная соль на пароль, параметры в БД. Токены: случайный токен, в БД — только SHA-256 хеш + `expires_at`. Секрет/настройки — в `.env`.
- **Роли:** `client` / `master` / `admin`. Роль определяется **только по БД** (`req.user.role`), никогда из body/query.

## Связь frontend ↔ backend
API RESTful под префиксом `/api`. Фронтенд при отображении переводит UTC из ответов в TZ салона (`SALON_TIMEZONE` из `.env`).

## Архитектура БД
8 таблиц: users, services, masters, schedule, bookings, blocks, tokens. Схема и триггеры создаются при `require('./src/db')` (idempotent, `IF NOT EXISTS`). Файл БД `src/db/booking.db` — в `.gitignore`.

## Бизнес-логика записи
**Одна общая функция** `createBooking()` в `src/bookings.js` для ВСЕХ ролей. Различия прав проверяются ДО вызова (в `server.js`):
- client → запись на себя (`client_id = req.user.id`);
- master → только на своего мастера (body.masterId игнорируется, берётся `masters.user_id = req.user.id`);
- admin → может указать `clientId` и `force_overlap`.
Сервер всегда сам вычисляет `end_time` по длительности услуги (клиент не задаёт длительность/стоимость/статус/роль).

## Расчёт свободного времени
`src/availability.js` → `getFreeSlots(masterId, date, durationMin)`. Динамически из графика + активных записей + блокировок. Слотов в БД нет.

## Транзакция (п.18)
Режим **`BEGIN IMMEDIATE`**. Почему: берёт exclusive-блокировку записи сразу при старте транзакции, до SELECT/INSERT. Это устраняет race condition, когда два параллельных запроса одновременно проверяют «свободно?» и оба решают «свободно» до вставки. Откат при любой ошибке (`ROLLBACK`). Ошибка блокировки (если БД занята) ловится и возвращается 500 без деталей.

## Защита от двойной записи (п.17)
Двухуровневая:
1. **Код** (`createBooking`): повторная проверка конфликта перед INSERT.
2. **БД** (триггеры `trg_bookings_no_overlap_insert` / `_update`): `BEFORE INSERT/UPDATE`, условие `start1 < end2 AND end1 > start2`, только для `status='active' AND force_overlap=0`. Отменённые не блокируют; вплотную стоящие не пересекаются.
При `RAISE(ABORT)` от триггера → перехват в `createBooking` → HTTP **409** + понятное сообщение + `availableSlots`.

## Версия Node.js
Требуется **Node.js >= 22** (встроенный `node:sqlite`). Проверено на v22.22.2.

## Требования для деплоя на BeGet
- Node.js 22+.
- `npm install` (только `express`).
- Создать `.env` из `.env.example`, задать `SESSION_SECRET` (>=32 символов).
- `node migrations/init.js` (создать БД/таблицы/триггеры).
- `node scripts/seed.js` (тестовые данные).
- `npm start` (порт из `.env`, по умолчанию 3000).
- BeGet должен разрешать запуск Node-процесса (не только static). Файл БД — на диске, в `.gitignore`.

## Результаты проверок (фактические)
См. итоговый отчёт (раздел 33 задания). Кратко:
- Регистрация: 201, пользователь в БД с scrypt-хешем.
- Логин верным паролем: 200 + токен. Неверным: 401.
- Свободное время: слот 11:00 исключён (есть запись 11:00–12:00).

## Реальные проблемы и исправления
### Проблема 1: мастер мог записать на ЧУЖОГО мастера
- **Причина:** `masterId` брался из body и проверялся до блока ролей; пустой `if` не блокировал.
- **Исправление:** для роли `master` `masterId` принудительно подставляется из `masters.user_id`; body.masterId игнорируется. Порядок проверки изменён (права → существование мастера).
- **Проверка:** мастер с `masterId=999` в body создал запись на своего master_id=1. ✅

### Проблема 2: формат времени в БД — `ISO с миллисекундами`
- **Причина:** `toISOString()` возвращает `2026-09-01T15:00:00.000Z`; ручные проверки по точной строке `'...Z'` не совпадали.
- **Исправление:** в тестах использовать диапазон, а не точную строку. Бизнес-логика (триггеры/availability) от этого не зависит — все сравнения консистентны (всё от `toISOString()`).
- **Проверка:** счётчик по диапазону показал ровно 1 активную запись. ✅

### Проблема 3 (проверка триггера): вставка мимо app
- Прямая SQL-вставка конфликтующей записи заблокирована триггером (`SLOT_CONFLICT`). Защита на уровне БД подтверждена. ✅
