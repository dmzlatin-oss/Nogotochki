# Отчёт по домашней работе — Сервис записи в салон/студию красоты

## 1. Общая идея проекта
Сервис записи клиентов в салон/студию красоты. Клиент регистрируется, входит, выбирает мастера и услугу, видит свободное время (динамически) и создаёт запись. Предусмотрены роли client / master / admin.

Страницы frontend: согласно заданию frontend будет подключён на следующих этапах; на текущем этапе реализован и проверен backend (API), к которому frontend подключается позднее.

Роли: client (клиент), master (мастер), admin (администратор).

## 2. Схема базы данных
Таблицы (8): users, services, masters, schedule, bookings, blocks, tokens. (фактически 7 таблиц; schedule и blocks — отдельные.)

Пример связи: `bookings.master_id → masters.id`. Запись связывает клиента (users), мастера (masters) и услугу (services). Длительность берётся из `services.duration_min`.

Вычисляемое значение: **свободные слоты** — не хранятся, рассчитываются динамически из графика мастера, активных записей, блокировок и длительности услуги (`src/availability.js`).

## 4. Три рабочие функции

### Регистрация и вход
- Данные: email `test1@example.com`, пароль `TestPass123`.
- Результат регистрации: HTTP 201, пользователь сохранён в БД с scrypt-хешем (отдельная соль, параметры N/r/p/keylen в `password_params`).
- Правильный пароль: HTTP 200, выдан токен (`/api/auth/login`).
- Неправильный пароль: HTTP 401, ответ «Неверный email или пароль» (не раскрывается, существует ли пользователь).

### Расчёт свободного времени
- Мастер: Ирина (id=1), график 09:00–18:00.
- Дата: 2026-09-01.
- Услуга: Маникюр (60 мин, id=1).
- Существующая запись: 2026-09-01 11:00–12:00 (UTC).
- Итоговые свободные слоты (UTC): 09:00, 10:00, 12:00, 13:00, 14:00, 15:00, 16:00, 17:00. Слот 11:00 исключён (занят записью).
- Интервалы, в которые помещается услуга 1 час: все вышеперечисленные слоты (каждый ровно 1 час свободен между занятыми/границами).

### Создание записи
- Пользователь: client (id=6, test1).
- Мастер: Ирина (id=1).
- Услуга: Маникюр (id=1).
- Дата/время: 2026-09-01 14:00–15:00 (UTC).
- Результат: HTTP 201, запись id=2 появилась в БД (status='active').

## 5. Конфликт слотов
- Как воспроизводили: два параллельных запроса (`Promise.all`) от двух клиентов (A и B) на один слот 2026-09-01 15:00–16:00.
- Ответ первому (A): HTTP 201, запись создана (id=3).
- Ответ второму (B): HTTP 409, `{"error":"SLOT_UNAVAILABLE","message":"Выбранное время уже занято","availableSlots":[...]}`.
- Результат в базе: ровно 1 активная запись на 15:00–16:00.
- Уровень защиты: триггеры SQLite (`BEFORE INSERT/UPDATE`, условие `start1<end2 AND end1>start2`, только active) + транзакция `BEGIN IMMEDIATE` + API 409.
- Дополнительно проверено: прямая SQL-вставка конфликтующей записи мимо приложения заблокирована триггером (`SLOT_CONFLICT`).

## 6. Проверка прав доступа
- Как проверяли: клиент A создаёт запись, клиент B (другой токен) делает `GET /api/bookings/<id записи A>`.
- Ответ сервера: HTTP 404 «Запись не найдена» (чужая запись не раскрывается).
- Где находится защита: `server.js` `GET /api/bookings/:id` — проверка `isClientOwner / isMasterOf / isAdmin` по БД; при отсутствии прав возвращается 404.

## 7. Самопроверка с помощью ИИ-ассистента
Запрос: «Проверь мой бэкенд...» (по заданию). Реальные находки:

Находка 1: Роль master могла записать на ЧУЖОГО мастера (masterId из body не блокировался).
- Решение: ИСПРАВЛЕНО. Для роли master `masterId` принудительно берётся из `masters.user_id`, body.masterId игнорируется. Проверено: мастер с `masterId=999` в body создал запись на своего master_id=1.

Находка 2: Rate limit реализован in-memory (сбрасывается при перезапуске процесса).
- Решение: ОСТАВЛЕНО как осознанное решение для учебного задания (достаточно для защиты от брутфорса на одном инстансе; для проде нужен Redis/shared store).

Находка 3: Непараметризованных SQL-запросов не обнаружено — все запросы используют `?`-плейсхолдеры (`node:sqlite`). Пароли только scrypt. Токены — хеш в БД.
- Решение: не требуется (соответствует требованиям).

## 8. Что сломалось и как вы это исправили
Проблема: мастер мог создать запись на произвольного мастера, передав `masterId` в теле запроса (нарушение «мастер работает только со своим расписанием»).
Причина: `masterId` проверялся из body до блока проверки ролей; пустой `if` не блокировал.
Как исправили: перенесли определение `masterId` по роли ДО проверки существования мастера; для `master` жёстко подставляем свой `master_id`.
Проверка: мастер с `masterId=999` в body получил запись на своего master_id=1 (подтверждено запросом к БД).
